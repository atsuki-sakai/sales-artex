# GPT-Liveを使う日本語の音声商談

2026年11月24日調査。音声モデルは11月19日に公開された `gpt-live-1.1` を使う。顧客がAIの発話に割り込んでも音声を受け取れる全二重モデルで、日本語を含む多言語の発音と文字起こしを改善した版である。音声はブラウザから直接OpenAIへ送る。Goは接続の認証と設定を担当し、毎フレームの音声中継を省く。対話の速さは、Goの実行時間だけでなく、マイク、ネットワーク、モデルの応答、再生まで含めて測る。[モデル仕様](https://developers.openai.com/api/docs/models/gpt-live-1.1)・[リリース履歴](https://developers.openai.com/api/docs/changelog)

## 接続から終了まで

| タイミング | 処理 |
| --- | --- |
| 開始 | 利用者の操作でマイクを開く。WebRTCにマイクのトラックと `oai-events` データチャネルを用意し、SDP offerをGoへ渡す。 |
| 接続 | GoがAPIキーを使って `POST /v1/live/sessions` に `session` と `transport: {type: "webrtc", sdp: offer}` をJSON送信する。成功応答の `transport.sdp` をブラウザの接続に設定する。 |
| 起動 | `session.started` を確認して制御イベントの送信を開始する。音声による起動を設定した場合、最初の発話で推論が始まる。音声はメディアトラック、字幕と制御はデータチャネルを使う。 |
| 会話中 | `session.input_transcript.delta` と `session.output_transcript.delta` を話者ごとに順に連結する。各断片の `start_ms` と `end_ms` はセッション開始からのおおよその位置。音響測定にはマイク信号を使う。 |
| 終了 | `session.close` 後に `session.closed` を待ち、最終利用秒数を読む。途中切断では、最後の累積値を暫定値として扱う。 |

Liveには会話の字幕が含まれる。初版の見積もりに独立した音声認識APIや音声合成APIは加算しない。別途検証用に録音を文字起こしする場合は、その処理に使うモデルの料金を加える。[WebRTC接続](https://developers.openai.com/api/docs/guides/voice-webrtc?api=live)・[セッション管理](https://developers.openai.com/api/docs/guides/live-conversations)

### 営業担当から話す場合と、顧客を待つ場合

既定はAI先行。開始時の `session.input` に開発者メッセージとして「今、日本語でAI営業担当と名乗り、登録された商材に沿って短く挨拶し、返事を待つ」と渡す。マイクのトラックは沈黙の間も有効に保つ。最初のAI字幕と再生音声を別々に確認する。モデルの生成タイミングにはばらつきがあるので、冒頭の発話開始までの時間も評価に含める。[先に挨拶するための公式手順](https://developers.openai.com/api/docs/guides/live-conversations#greet-before-the-caller-speaks)

費用を抑えるモードでは、開始時に `wake_policy.type = speech` と `idle_timeout_s = 15` を指定する。顧客の第一声で推論を開始し、無発話が続くと待機料金に切り替わる。AI先行では開始直後から通常料金の対象になる。1分間相手の準備を待つ場合は、通常状態が続けば$0.05、全区間が待機なら$0.02という差になる。どちらを選んでも、申込意思は本人に復唱して確認し、正式な契約・署名は別の業務で扱う。このアプリでは担当者への連絡も実行できない。[待機時の挙動](https://developers.openai.com/api/docs/guides/live-conversations#managing-idle-sessions)・[音声費用](https://developers.openai.com/api/docs/guides/voice-latency-cost?api=live)

## 「内なる独白」を会話に生かす

内なる独白は、商談中に更新する短い作業メモとして設計する。保持したい情報は「顧客が明言したこと」「確認が必要な点」「次に一つ尋ねるなら何か」。例えば「月額はどれくらいですか」が根拠なら、価格に質問があったことを記録し、予算や購入意思は未確認とする。声の高さはHz、テンポは時間あたりの観測値として扱う。録音環境や個人差があるため、それらから成約確率を算出する根拠は現時点でない。

1. **会話を継続する。** 音声モデルは顧客の質問に短く答え、割り込み時は聞き手に回る。新しい発話を音声分析や長い推論の完了待ちにしない。
2. **専門ごとに根拠を集める。** ローカルルールで抽出した論点は、操作者の画面とテキストデモに使う。音声モデルへの指示には使わない。例えば価格の質問と導入時期への言及を別々に扱い、それぞれを元の発言に結び付ける。同じ発言中の「価格には関心がない」も検証用データに含める。
3. **次の一手を一つ選ぶ。** 料金を聞かれたら登録情報から答える。金額が未登録ならその場で分かる範囲を伝える。追加の質問は回答を変える事実が欠けている場合に限る。顧客が辞退した場合はその意向を優先する。見積依頼や次回面談の日程に合意した段階と契約成立を区別する。
4. **短いメモを反映する。** `session.thinking.append` に自然な日本語を短く渡す。セッション共通メモは `delegation_id: null`。1件500トークン以内で、顧客の発言をそのままシステム命令に組み込まない。内容は後の返答に表れる可能性があるため、内部の採点、秘密情報、モデルの思考過程は載せない。
5. **複雑な質問だけ追加推論する。** `SALES_EXPERT_MODEL=gpt-6-luna` を設定すると、複雑な相談を検出したとき、相手の発話後に最初のAI出力字幕を受けてからGoが独立して公式Decisions APIを呼ぶ。三つの観点から応対方針を選び、追加助言が不要ならメモを送らない。相手の発言が更新されたら古い結果を破棄する。他の専門モデルを指定した場合はResponses APIを使う。複数の専門家の合議は、初版ではこの複数の観点とローカルルールで表現する。独立モデルの意見を比較する方式に拡張する際は、後述の評価で追加費用に見合う改善を測る。

例えば非同期のメモは次の形式をとる。

```json
{
  "type": "session.thinking.append",
  "event_id": "plan_12",
  "delegation_id": null,
  "content": "この相談への参考：顧客が示した条件を使い、登録情報で裏づけられる違いを伝える。"
}
```

送信するのは変化のあった論点だけとする。モデルへの反映中に相手が訂正した場合は、新しい発言を優先する。`session.thinking.appended` は文脈がモデルに届くタイミングを表す。実際にどの返答に反映されたかは出力音声で評価する。提案金額や条件について正確な社内情報が必要なら、将来は承認済み商品表を照会し、取得できた値を返す。[Liveプロンプト](https://developers.openai.com/api/docs/guides/live-prompting)・[非同期の委譲](https://developers.openai.com/api/docs/guides/live-delegation)・[セッションへの文脈追加](https://developers.openai.com/api/docs/guides/live-conversations#add-context-during-the-conversation)

## 1商談と月間の費用

公表単価は米ドルで、通常時は毎分 **$0.05**、WebRTCの推論停止中は毎分 **$0.02**。請求単位は秒。下記は税、為替、サーバー、電話網、追加推論を含まないWebRTC音声部分の試算。初版の利用時間上限を15分とし、5分または15分の商談を例に、終了処理や再接続による追加時間を除いて計算した。[公式料金表](https://developers.openai.com/api/docs/pricing#live-session-duration)

| 1商談の内訳 | 1件 | 月100件 | 月1,000件 |
| --- | ---: | ---: | ---: |
| 通常5分 | $0.25 | $25 | $250 |
| 通常10分＋待機5分 | $0.60 | $60 | $600 |
| 通常15分 | $0.75 | $75 | $750 |

式は `音声費 = 通常秒数 × 0.05 / 60 + 待機秒数 × 0.02 / 60`。15秒の無発話で待機に戻る設定でも、そこに至る15秒は通常料金となる。発話前の資料閲覧などで5分を実際に待機状態にできれば、通常15分の場合より1件$0.15、1,000件で$150抑えられる。待機復帰直後の短い問いへの返答が遅れる場合があり、商談で待機に入る頻度も同時に見る。[音声費用の解説](https://developers.openai.com/api/docs/guides/voice-latency-cost?api=live)・[待機設定](https://developers.openai.com/api/docs/guides/live-conversations#configure-standby)

ローカル分析の追加API費用はゼロ。現在の `gpt-6-luna` 専門分析ではDecisions APIを使い、通常の未キャッシュ入力100万トークンあたり$0.10、出力は無料。1商談6回、1回あたり入力1,000トークン、キャッシュや地域加算なしなら追加は$0.0006。通常15分の音声とこの追加専門分析の小計は1件$0.7506、1,000件で$750.60。会話制御に使うネイティブ字幕トリガーの使用分はこの試算の対象外。別モデルを指定してResponses APIを使う場合は、そのモデルの入出力単価が適用される。[Decisionsの料金](https://developers.openai.com/api/docs/guides/decisions#pricing-and-availability)

### 支出を下げる順序

- **使う直前に開始し、終わったら明示的に閉じる。** マイクのミュートだけでは課金は続く。通常のWebRTC起動には初期化15秒の請求があり、開始済みのセッションの音声時間に充当される。完了した商談の見積もりに再加算しない。自動再接続の連打は別セッションの作成を増やす。[初期化と課金](https://developers.openai.com/api/docs/guides/voice-latency-cost?api=live#webrtc-initialization-charges)
- **聞き取りと分析を並行させる。** 全字幕を専門家ごとに送り直さず、簡単な分岐はローカルで済ませる。聞き返しを減らすため、商材名、提示可能な条件、希望する次の行動は開始時に渡す。外部での確認が必要なら、分かっている条件と未確認の事項をその場で伝える。
- **請求と成果を突き合わせる。** 運用時には `session.usage.updated` の累積秒数を上書きし、最終イベントの総秒数を1回集計する。推論の稼働・待機の区間情報と照合し、追加分析にはDecisionsまたはResponsesの使用量・請求記録を用いる。全費用を「次回面談を合意できた件数」など事前に決めた成果数で割れば、短い失敗商談ばかりの設定を選ぶのを避けられる。[利用量集計](https://developers.openai.com/api/docs/guides/voice-latency-cost?api=live#monitor-actual-usage)

## 実際の顧客に使う前の評価

精度、応答時間、成約率を検証するための評価案を示す。日本語の模擬商談を録音し、価格への質問、導入時期、明示的な辞退、途中訂正、割り込みを人がラベル付けする。同じケースを条件別に再生し、端末、マイク距離、雑音の有無も記録する。[OpenAIの音声エージェント評価ガイド](https://developers.openai.com/cookbook/examples/audio/voice_agent_evaluation)

| 対象 | 比較・集計する指標 |
| --- | --- |
| 声の高さ | 複数周波数のテスト信号でHzの誤差を確認した後、日本語の有声音で参照値と照合。無声区間、雑音、倍音を基本周波数と誤認した率も数える。 |
| 話すテンポ | 文字数/秒を使う場合、同じ発話の人手字幕、対象区間、句読点の扱いをそろえる。言いよどみ、漢字・かなの揺れ、モデルによる字幕訂正で変動する。 |
| 関心と異議 | 人が引用した根拠発話に照らし、論点ごとの適合率と再現率を出す。根拠不足を未判定にできた件数や、否定を肯定と誤認した数も見る。 |
| 対話遅延 | 発話終了から最初に再生された有用な返答音声までのp50・p95を、通常時と待機復帰時で比較。字幕の到着、相づち、本題の返答は別に時刻を取る。 |
| 商談結果 | 同じ商品条件・シナリオで、音声のみ、ローカル分析付き、追加推論付きの3条件を比較。顧客の疑問解消、誤った価格の提示、明示的な次回合意、費用/合意件数を記録する。実契約は署名など別の確定情報で評価する。 |

### 初版のローカル計測

Apple M3 Pro、Node.js 22.14.0で計測した。各試験の先頭100回をウォームアップとして除外し、1回の処理時間を `performance.now()` で測定した。

| 処理と条件 | 計測回数 | p50 | p95 |
|---|---:|---:|---:|
| 音響1フレームの追加。48kHz・2,048サンプルの160Hz正弦波を20ms刻みで入力 | 1,000 | 0.047ms | 0.183ms |
| 15分相当の模擬字幕1,500断片を結合し、見立てと商談手法を再計算。600msごとに交互の発話を配置 | 400 | 0.964ms | 1.531ms |

この値の対象は音響・商談ロジックのCPU処理である。ブラウザ描画、実機マイク、WAN、OpenAIの推論、相手の耳に音が届くまでの時間は別計測となる。実商談の体感を判定するには、前表の「対話遅延」を計測する。

## 公式のアプリとSDKを使う場合

- **OpenAI Live Console** はMITのローカルサンプル。架空の商品カタログについて音声で質問し、どの質問が裏のモデルに渡り、いつ回答になったかを画面で追える。調査時の版は `gpt-live-1` と `gpt-5.4-mini` が既定で、商品情報の照会をバックエンドに回す作り。商談デスクとはモデルとプロンプトが異なるため、速度の比較には同一条件が必要になる。[サンプルのREADME](https://github.com/openai/openai-live-console/tree/5f64ecb3009d8274da9953c825d469ea6b6b67c3)
- **公式SDKとWebRTC**。OpenAIのTypeScript SDKでは `client.live.create` がサーバー側の接続交渉を担当し、Go向けの公式例もある。ブラウザではどちらもWebRTCのメディアトラックで音声を扱う。商談デスクは同じ公式APIをGoのHTTPクライアントから利用している。[WebRTC公式実装例](https://developers.openai.com/api/docs/guides/voice-webrtc)・[TypeScript SDK](https://developers.openai.com/api/reference/typescript/resources/live/methods/create)
- **営業分析**。OpenAIには音声から選択肢を判定するDecisionsの公式機能がある。字幕断片ごとのネイティブトリガーにも対応する。この商談デスクでは費用と送信回数を抑えるため、複雑な質問に絞って `/v1/decisions` を呼ぶ。応答開始済みの発言に対する助言は短い内部メモとして扱う。[音声とDecisionsの連携](https://developers.openai.com/api/docs/guides/decisions-voice)

### 応答待ちの調査と変更（2026年11月24日）

旧版は比較の相談で専門モデルに委譲し、結果を確認してから答える指示を含んでいた。実際の日本語の合成音声をヘッドレスChromeから送り、本物のAPIに接続した試験の一つで、委譲の開始から完了まで4.48秒かかった。別の試行では同じ相談に委譲が発生しなかった。利用者が最初に試した通話の記録は残していない。

現在はGPT-Liveが登録済みの知識で直接答える。顧客の入力後にAIの最初の出力字幕を受け、比較などに該当する場合だけ専門分析を開始する。助言は非同期で音声モデルに届け、相手が話を続けた場合は古い分析を中断する。予告の読み上げを減らすため、クライアントへの委譲要求には短い非発話の文脈で応じる。800msの `acknowledgement_delay_ms` は自動応答予告を抑制するための猶予で、通常の音声応答を遅らせるタイマーではない。[公式の自動予告制御](https://developers.openai.com/api/docs/guides/live-delegation#suppress-automatic-acknowledgments-while-tools-run)

専門分析を4秒止めた模擬接続では、分析完了の3.98秒前に回答字幕を観測した。実APIでもDecisionsの選択結果が画面に届き、音声通話が終了した。割り込みを含む日本語の試行では、質問の音源末尾からAI音声の受信まで1.65秒、アプリのエネルギー閾値による推定は1.98秒だった。端末での検出はマイクの音量・音の重なり・周囲の音の影響を受ける。画面の数値には相づちも含み得るため、実質的な回答かどうかは字幕と音声で確認する。

冒頭の挨拶が終わって静かになってから、同じ日本語の質問音声を流した比較結果を下表に示す。各版1回。時刻の起点は質問の音源末尾。

| 観測箇所 | 旧版 | 変更後 |
|---|---:|---:|
| 入力字幕の確定相当 | 1.17秒 | 1.19秒 |
| 本題の最初の字幕 | 2.32秒 | 2.29秒 |
| ブラウザでのAI音声の立ち上がり | 2.59秒 | 2.72秒 |

この比較の旧版では専門家への委譲は発生しなかった。変更後は専門分析が実APIで411msで完了し、画面の音声待ち時間は2.68秒だった。専門分析と返答を並行して進められることは確認できたが、通常の返答の短縮はこの比較では確認できなかった。

### 挨拶や説明に割り込む

旧版でもマイクは開いていたが、顧客とAIが同時に話したときもブラウザは受信した音声を再生し続けていた。現在はマイクと受信音声を並行して観測し、発声が重なったらブラウザ側でAIの再生をいったん抑える。音を抑えた後にも顧客の声が続けば、古い専門分析を取り消し、`session.instructions.append` で直前の説明を打ち切るようGPT-Liveに伝える。マイクとWebRTC接続は維持する。再生再開の判定には顧客の発声と受信音声の静かな区間を使う。短い雑音・回り込みを排除するための判定は音響上の推定であり、短い「はい」が相づちか制止かを意味で分類する機能はない。[OpenAIの再生制御](https://developers.openai.com/api/docs/guides/voice-server-controls#control-playback-when-needed)

Decisionsの音声ガイドにある字幕トリガーは、相手の発言内容から選択肢を判定したい場合に使える。字幕や判定結果は音声と別に届くので、端末で音を止める経路はこれらの完了を待たずに動かす。音の重なりを検知する処理は端末で実行する。入力字幕では別にネイティブDecisionsの判定を受け、待機、再開、終話を制御する。[音声とDecisionsの公式ガイド](https://developers.openai.com/api/docs/guides/decisions-voice#react-to-transcripts)

実APIに接続したChromeで、挨拶中に同じ3.98秒の日本語音声「ちょっと待ってください。月額料金だけ教えてください」を重ねた。旧版では顧客の発声開始から3.03秒後まで挨拶が断続的に再生された。最初の修正では0.89秒だった。短い音節や息継ぎの間に検出がリセットされる挙動も修正した最終版では、最後の再生音が発声開始の0.37秒後だった。元の受信トラックにはAI音声が残っていても、再生側はそこから顧客が言い終わるまで無音で、質問終了の1.37秒後に試験用の登録料金「月額千円です」と返答した。最終版の中断命令の送信は発声開始の0.48秒後、受領イベントは1.57秒後だった。各版1回の合成音声試験で、測定点はChromeの再生用トラック。実機スピーカーの物理出力や周囲の雑音は計測していない。

### 同じ日本語音声での話者交代の比較

2026年11月24日、同じChromeとLive APIで変更前後に同じ合成音声を流した。「このソフトの月額料金はいくらですか」は挨拶が終わってから、「ちょっと待ってください。月額料金だけ教えてください」は挨拶中に再生した。返答の開始は、音源の発話末尾からブラウザの再生用トラックに最初の音が出るまでで測った。

| 観測した時間 | 変更前 | 今回の変更後 |
| --- | ---: | ---: |
| 通常の料金質問から返答開始まで（各3回の中央値） | 1.403秒 | 1.407秒 |
| 割り込みの発声開始から再生トラックの消音まで（各1回） | 0.341秒 | 0.133秒 |
| 割り込みの発声開始から挨拶の最後の音を観測するまで（同じ試行） | 0.117秒 | 0.164秒 |
| 割り込みの質問が終わってから返答開始まで（各1回） | 1.716秒 | 1.373秒 |

通常の返答時間はほぼ同じで、6回すべてで登録料金を最初に答えた。通常応答の指示を詳しくした案の中央値は1.768秒、商談指示全体を短くした案は1.593秒だった。採用した指示では、相手の発話中に答えを準備することを一文だけ加えた。

「ええと、月額……ではなく、初期費用はいくらですか」の途中に0.5秒の間を入れた試験では、その間は無音だった。相手が話を続けた後に約0.09秒の相づちがあり、質問を言い終えた1.42秒後に「初期費用は三千円です」と答えた。これらは合成マイクとブラウザでの観測値で、実際のマイクやスピーカーでの体感には機器と回線も影響する。

実通話の比較後、顧客の語尾と新しい返答が40〜60msだけ重なる通常の交代を回帰テストに加えた。AIが話す前のマイク入力を割り込み時間に数えると、返答の冒頭まで消音してしまう。修正後はこの区間を再生でき、同じ割り込み試験の音源と受信音の時系列を20ms刻みで再現しても、発声開始から120msで消音、320msで中断確定になった。

### 会話の意味と実行できる業務

営業側の目標は顧客の発言を解釈する根拠にはならない。料金や機能は商材欄、希望と訂正は本人の発言から判断する。確認に時間が必要と言えるのは、実際に照会を開始して結果を待っているとき。今回の商談デスクで扱えるのは会話と画面上の記録で、カレンダー照会・予約・人への送信の接続先はない。

| 顧客が伝えたこと | 次に行うこと |
| --- | --- |
| 自動化したい工程を既に特定した | 登録機能でできる部分と、本人に残る作業を説明する。答えが変わる場合だけ追加条件を聞く |
| 料金を尋ねた | 登録額があれば回答し、金額が未登録ならこの場では分からないと伝える |
| デモの候補日時を提示した | 希望日時として受け取る。予約確定には別途、空き枠確認と予約処理が必要 |
| しばらく聞いてほしいと頼んだ | AIの音声を止め、顧客が発言できる状態を維持する |
| 自分が待つ必要があるのか質問した | 質問として答える。外部で処理中の業務がないなら待ち時間を求める理由はない |
| 今の通話を終えるよう依頼した | 新しい案内を止めて接続を閉じる。商品の辞退、作業の終了、引用は通話終了の根拠にならない |

端末の単語ルールは操作者向けの参考表示に使う。会話全体の意味を決める命令としてLiveに渡すと、すでに答えた課題に対しても次の質問が送られる。専門モデルは助言不要を選べる。音声の割り込みとは別に、入力字幕にひもづく `decision.event` で顧客の待機・再開・終了の希望を受け取る。新たな顧客発言があれば古い判定を破棄する。終話だけは取り消しがきかないため、声と字幕が1.2秒落ち着くのを待って `session.close` を送る。[公式の字幕トリガー](https://developers.openai.com/api/docs/guides/decisions-voice#react-to-transcripts)

実モデルの回帰評価は、音声セッションと同じ判定質問を使い、日本語の別表現12件に対して完結したテキストの意味を判別できるか調べる。継続と終了、質問と待機、用件だけの辞退と会話全体の終了を含む。部分字幕の到着順、言い直し、再生・切断はブラウザ側で別に検証する。[評価コード](../conversation_eval_test.go)

**今回の通話確認**。商談デスクの通常の開始ボタンからChromeで2回接続し、冒頭15秒は顧客側を無音にした。マイク入力はChrome標準のファイル仮想デバイスに与えた日本語の合成音声。アプリのマイク取得処理・WebRTC・Live APIを使用した。肉声や物理スピーカーは対象外。

- 1回目は料金が未登録であること、面積・単価を入力して見積書を作れることを登録資料の範囲で回答した。木曜20時は希望として受け取り、予約を確定できないと答えた。顧客の終話依頼に対してサーバーの `session.closed` を受けた。
- 2回目は「今は聞いていて」という依頼後、再生トラックに約16秒間の無音を確認した。次の料金質問で手動操作なしに再生が戻り、最後は終話依頼により接続が閉じた。料金の回答後に機能説明も一文加えており、毎回最短の回答になるわけではない。
- 待機中にもモデルが「はい、承知しました」と字幕を生成した。画面は再生抑制中に受信した字幕を区別して表示し、その文面を「顧客に説明した内容」として専門分析に渡さない。生成字幕の時刻と再生音声は別に観測する。WebRTCの音とデータチャネルは別に流れるため、字幕だけでは顧客が耳にした文面を特定できない。

## 応答速度と自然な話者交代の改善候補（2026年11月24日）

### 料金質問の1.4秒はどこで生じたか

上記の変更後の通常質問3回について、既存のChrome計測ログを同じブラウザ時計で再集計した。起点は合成音声「このソフトの月額料金はいくらですか」の発話末尾。字幕は3件とも料金回答の冒頭だった。

| 試行 | 最初の回答字幕を受信 | 再生トラックで最初の音を検出 | 字幕から音まで |
| --- | ---: | ---: | ---: |
| 1 | 0.995秒 | 1.407秒 | 0.412秒 |
| 2 | 1.048秒 | 1.529秒 | 0.481秒 |
| 3 | 0.974秒 | 1.300秒 | 0.326秒 |

3回とも受信元の音声トラックと再生用トラックで、15ms周期の同じ観測時点に最初の音が出た。この条件ではアプリの消音解除による追加待ちは観測されなかった。字幕はデータチャネル、音声はWebRTCのメディアトラックを流れるため、表の差だけからモデルの推論時間・ネットワーク・受信バッファを個別には求められない。物理スピーカーの出音も別途測る必要がある。[Liveの字幕と音声](https://developers.openai.com/api/docs/guides/live-conversations)

### 効果を確かめる順序

以下の比較を実施した結果と、通常質問・相づち・割り込みの実際の音声は、[日本語音声通話の比較試験](voice-trial-2026-11-24/report.md)にまとめた。

1. **日本語の発話とWebRTC統計を一緒に測る。** 既存のシナリオに、本人の同意を得た肉声の短い返事、言いよどみ、料金・日付の訂正を加える。通常質問では発話末尾から初音までと、金額など本題が聞こえるまでを記録する。割り込みでは消音指示と最後に聞こえた旧音声を別々に記録する。各ターンで接続の往復時間、パケット損失、受信バッファでの平均滞留時間（同区間の `jitterBufferDelay` の差分を `jitterBufferEmittedCount` の差分で割る。分母が0の区間は除外）を照合する。アプリの表示値は短い音声や重なりを除くため、評価では測れなかった件数・無応答も残す。[OpenAIの音声評価ガイド](https://developers.openai.com/cookbook/examples/audio/voice_agent_evaluation#metrics)・[W3CのWebRTC統計](https://www.w3.org/TR/webrtc-stats/#dom-rtcinboundrtpstreamstats-jitterbufferdelay)
2. **通常応答の短縮には、Realtime APIを同条件で試す。** 現行の `gpt-live-1.1` を基準に、高速応答向けの `gpt-realtime-2.1-mini` をWebRTCで比較する。Realtime側で発話内容から終わりを判断する `semantic_vad` の `eagerness` をまず `auto`、次に `high` とし、同じ音源・商材・端末・回線で順番を入れ替えて繰り返す。音声が早くても訂正前の金額を答えたり、相手の思考中に割り込んだりする設定は採用しない。Liveの字幕イベント・Decisions連携とRealtimeの発話／キャンセルイベントは異なるため、まず検証用の接続で比較する。この商談条件での短縮幅は未測定。[Realtime miniのモデル仕様](https://developers.openai.com/api/docs/models/gpt-realtime-2.1-mini)・[Realtimeの発話終了判定](https://developers.openai.com/api/docs/guides/realtime-vad)・[割り込みと発話履歴](https://developers.openai.com/api/docs/guides/realtime-conversations#interruption-and-truncation)
3. **Liveの自然さは相づち・制止・訂正を別々に調整する。** 「はい」は説明を聞いている途中と質問に答える場面の両方を試す。「ちょっと待って」では声を譲り、「初期費用、ではなく月額」では訂正後の用件に答え、「続きをお願いします」では消音中の説明を相手が聞いた前提で進めないことを確認する。比較する指示は一度に一項目とし、正答率、早すぎる割り込み、無応答、応答時間の中央値と90パーセンタイルを件数付きで残す。試験規模の案は各場面・各条件10回で候補を絞り、有望な条件は30回に増やす。人間の対面会話では応答の最頻域が0〜200msだった研究があるが、質問の種類や身振りの有無で変わるため、この商談では同じ日本語の場面同士を比べる。[Liveの相づち・割り込みの指示例](https://developers.openai.com/api/docs/guides/live-prompting)・[会話の話者交代を10言語で調べた原著](https://pmc.ncbi.nlm.nih.gov/articles/PMC2705608/)

**商談の正答率を上げる小さな比較。** 既存の商材欄に、月額、初期費用、税込・税別、適用条件、資料で未確認の事項を分けて書く。商材名に特有の読みがあれば添える。同じ商品情報を文章だけで渡す場合と比べ、最初の一文で正しい料金を言えた割合と不要な聞き返しの件数を取る。日付や金額が聞き取りにくい場面では、その箇所だけ確認する。文章形式と項目別形式の試行結果は、上記の比較試験を参照。[OpenAIの発音・数字の扱い](https://developers.openai.com/api/docs/guides/live-prompting#unclear-names-dates-and-numbers)

タイマーごとの用途も異なる。Liveの `wake_policy.vad_threshold` は初回・待機復帰の検知に使い、`acknowledgement_delay_ms` は専門処理中の自動予告までの猶予を決める。WARPが短縮するのはWebRTCの接続開始である。現行では専門分析も返答字幕の後に始まる。したがって、通常の料金質問ではこれらの変更より上の比較を優先する。[LiveセッションAPI](https://developers.openai.com/api/reference/resources/live/methods/create)・[委譲の自動予告](https://developers.openai.com/api/docs/guides/live-delegation#suppress-automatic-acknowledgments-while-tools-run)・[WebRTC WARP](https://developers.openai.com/api/docs/guides/realtime-webrtc-warp)
